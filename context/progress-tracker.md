## Architecture Decisions

- **Stack:** Next.js 16 + TypeScript, Tailwind + shadcn/ui, Supabase (PostgreSQL + Auth + Storage), hosted on Vercel. All free tier.
- **Auth:** Supabase Auth, single owner, email / password; row-level security enforced with `auth.uid()`.
- **Data access:** Supabase client with generated TypeScript types (no Prisma).
- **Reusable backend:** Supabase is the single source of truth so future iOS / Android apps share it; keep shared logic (inbreeding check, stage derivation) as portable functions in `lib` that can move to a Supabase function later.
- **Barns are core:** every goat is assigned a barn at registration; `barn_id` is nullable in the database for edge cases. Grouped so a future Farm → Barn → Goat layer can be added without rework.
- **Goat stage** (Doe, Doeling, Buck, Buckling, Wether, Kid) is derived from sex, age, and reproductive state — not stored. Thresholds confirmed with the owner (2026-08-26): `kidMax: 6` months, `youngStockMax: 12` months, general-purpose rather than breed-specific; kept in one place (`lib/goats/stage.ts`) so they're easy to retune per breed later.
- **Goat identifier:** per the owner (2026-08-26), `tag` is the required identifier on a goat record and `name` is optional — the reverse of the original spec draft. Every later spec/UI referencing a goat's "name" should treat `tag` as the fallback display label when `name` is blank (see `goat.name ?? goat.tag` in the goats list/detail pages).
- **New-table id convention:** `barns` (04) set the real convention as `bigserial` integer ids with a single `"owner full access" for all` RLS policy, not the `uuid` + four-policy style shown in some spec drafts. `goats` (05) followed suit; later specs creating new tables should match this too unless there's a specific reason not to.

- **Base UI `Select` trigger display:** this shadcn/Base UI `Select` only shows a submitted value's real label in the closed trigger if the `Select` root is given an `items` array (`{ label, value }` pairs); without it, the trigger displays the raw `value` string verbatim. Any `Select` whose values aren't already human-readable on their own (sentinels like an "Other…" placeholder, or opaque ids like a barn's numeric `id`) needs `items` set, or it'll silently show internal/meaningless text to the owner. Selects whose values already read fine on their own (e.g. `sex`, `status` — lowercase but legible words) don't strictly need it, though it would be a worthwhile cosmetic pass later.
- **Dialog trigger convention (`ERR-001`, 2026-08-28):** a form dialog must never accept a pre-built trigger element (e.g. `trigger: ReactElement`) from a Server Component caller — passing a client `<Button>` element across the RSC boundary into base-ui's `DialogTrigger render={...}` resolves `data-slot` differently on SSR vs. the client and causes a hydration mismatch. Every dialog instead builds its own trigger internally from plain props (`triggerLabel`, `triggerIcon`, `triggerVariant`, `triggerSize`), as `GoatFormDialog` and `BarnFormDialog` now do. Any new add/edit dialog should follow this shape from the start rather than the old element-prop pattern.
- **Breed is a composition, stored in a child table** (`06`, 6b, 2026-08-28): `goat_breed_composition` (one row per breed component, `pct numeric(6,3)`), replacing `05a`'s two `goats` columns. Chosen over a JSON column for RLS consistency (one `"owner full access"` policy, like every other owned table) and easy querying. `goats.breed` is **kept** as a denormalised primary-breed label so list/table views don't need a join. The sum-to-100 rule is enforced app-side in `validateComposition` (`lib/goats/breeds.ts`), not a DB trigger — sufficient for v1. `BreedComposition` is `{ breed: string; pct: number }[]`; a purebred goat is one row at 100, a manual cross is two rows at 50/50, and parent averaging (`composeFromParents`) can yield three or more rows.
- **Pedigree / ancestry walk is pure `lib` logic** (`06`, 6a): `lib/goats/pedigree.ts` — no React, no Supabase, callers pass an in-memory `Map` of goats. Cycle-safe (a goat repeating on its own path becomes a leaf). `PEDIGREE_MAX_GENERATIONS = 4` in one place; **spec 09's inbreeding check must reuse `buildPedigree` / `collectAncestorIds` from here** rather than re-walking `sire_id`/`dam_id` itself (invariant 6).
